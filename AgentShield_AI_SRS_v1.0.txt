1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the functional and non-functional requirements for AgentShield AI — a behaviour-based security monitoring system designed to observe, analyze, and evaluate the actions of autonomous AI agents. This document serves as the authoritative reference for the design, development, testing, and evaluation of the system.
This document is intended for the project development team, the academic guide, and examiners at IMS Engineering College, Ghaziabad, as part of the 4th year major project submission.
1.2 Scope
AgentShield AI is a monitoring and threat detection platform that:
Captures and logs all actions performed by autonomous AI agents in real time
Applies rule-based security policies to detect known threat patterns
Uses machine learning (Isolation Forest) to detect novel or anomalous agent behaviour
Computes dynamic risk scores for individual agents and their actions
Presents findings through a centralized React.js security dashboard with alerts
The system does not directly control or restrict AI agents; it operates as a passive observer and active alerting layer. The initial version targets simulated AI agent environments for demonstration and evaluation purposes.

2. Overall Description
2.1 Product Perspective
AgentShield AI operates as an independent monitoring layer that interfaces with AI agent environments through an event ingestion API. It does not replace existing security tools (firewalls, SIEM systems) but complements them by providing semantic-level visibility into AI agent behaviour — a gap that traditional security tools do not address.
The system follows a 4-layer architecture:
Agent Simulator Layer — generates synthetic AI agent activity logs
Ingestion and Processing Layer — FastAPI backend receives and evaluates actions
Storage Layer — PostgreSQL persists all events, scores, and alerts
Presentation Layer — React.js dashboard displays analytics and alerts
2.2 Product Functions
The primary functions of AgentShield AI are summarized below:

2.5 Design and Implementation Constraints
The MVP (Minimum Viable Product) uses simulated AI agent activity; integration with production agents is a future scope item
ML model training is performed offline on historical log data; real-time inference only at v1.0
All communication between frontend and backend must use HTTPS/WSS in production
The system must remain functional with up to 50 concurrent simulated agent sessions
Risk scoring algorithm must complete within 200ms per action to support real-time operation
2.6 Assumptions and Dependencies
AI agent activity can be represented as structured JSON events containing action type, parameters, agent ID, and timestamp
The Isolation Forest model is pre-trained on a representative dataset of normal agent behaviour before deployment
PostgreSQL database is available and accessible from the FastAPI backend
The development team has working knowledge of Python, React.js, and PostgreSQL
MITRE ATLAS threat taxonomy is used as the reference framework for defining security rules

4.2 Main Flow — Action Ingestion to Alert
The following sequence describes the primary detection flow:
AI Agent Simulator sends a POST request to /api/v1/actions with a JSON action event payload
FastAPI backend validates the payload schema; returns 422 if invalid
Valid event is written to the actions table in PostgreSQL with a generated action_id
Rule Engine evaluates the action against all enabled rules; rule matches are recorded
Feature vector is extracted from the action and added to the current scoring batch
Every 60 seconds, the ML Engine runs Isolation Forest on the accumulated batch; anomaly scores are written back to the actions table
Risk Score is computed per action using the weighted formula (FR-16)
If risk score exceeds the configured threshold, an alert record is inserted into the alerts table
Dashboard polls /api/v1/alerts every 5 seconds; new alerts appear as notifications
Analyst acknowledges the alert, adds investigation notes, and marks it resolved
4.3 Entity Relationship Overview
The core data relationships are:
One Agent has many Actions (one-to-many: agents → actions)
One Action may trigger zero or more Alerts (one-to-many: actions → alerts)
One Rule may match many Actions; each match is recorded in the alerts table with the triggering rule_id
Audit Log records all system-level events independently with no foreign key dependencies (append-only)

5.2 Component Descriptions
5.2.1 AI Agent Simulator
A Python script that generates synthetic AI agent action sequences following configurable behaviour profiles — including normal workflow patterns and injected threat scenarios (unauthorized file access, API flooding, prompt injection patterns). Outputs JSON events to the ingestion API.
5.2.2 FastAPI Backend
The central processing hub. Handles request validation, coordinates the Rule Engine and ML Engine, computes risk scores, and writes all results to PostgreSQL. Exposes both REST endpoints and WebSocket connections. Implements JWT authentication for all protected routes.
5.2.3 Rule Engine
A synchronous evaluation module that compares each incoming action against the rules stored in the PostgreSQL rules table. Rules are expressed as JSON condition objects and evaluated using a lightweight expression evaluator. Returns a list of matched rules and their aggregate severity score for use in risk calculation.
5.2.4 ML Engine
An asynchronous batch processing module that runs every 60 seconds. Loads the latest pre-trained Isolation Forest model from disk, extracts feature vectors from the current action batch, computes anomaly scores, and writes them back to the actions table. Supports model retraining via an admin-triggered endpoint.
5.2.5 React.js Dashboard
A single-page application providing the operator interface. Polls the FastAPI backend at 5-second intervals for updated data. Uses Chart.js for risk trend visualization. Implements real-time alert notifications, agent drill-down views, and rule management interfaces. Communicates exclusively with the FastAPI backend via HTTP/WebSocket; it has no direct database access.
